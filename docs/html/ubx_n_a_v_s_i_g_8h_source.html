1/*
2 ubxNAVSIG.h
3
4 v4 scaffolding: UBX-NAV-SIG - implemented as its own Class, per AGENTS.md
5 "Implement each UBX message in its own Class". Like NAV-SAT (see ubxNAVSAT.h), NAV-SIG's
6 payload is variable length: a fixed 8-byte header (iTOW, version, numSigs) followed by
7 0..UBX_NAV_SIG_MAX_BLOCKS identically-shaped 16-byte per-signal blocks - see u-blox_structs.h's
8 UBX_NAV_SIG_header_t/UBX_NAV_SIG_block_t and AGENTS.md "Adding the variable-length UBX
9 messages". This is the second (and, for now, last) message migrated using that mechanism -
10 NAV-SAT was the worked example; nothing new needed designing here, the same approach applies
11 directly.
12
13 'ubxFields' below describes the header only, read with the ordinary
14 getUbxMessageField()/getUbxMessageFieldCallback(). 'ubxBlockFields' describes one repeated
15 block, with offsets relative to the START OF THE BLOCK (not the message) - read with
16 getUbxMessageBlockField()/getUbxMessageBlockFieldCallback(), passing the block index
17 (0..numSigs-1) returned by the "numSigs" header field above.
18
19 messageLength is set to UBX_NAV_SIG_MAX_LEN - the MAXIMUM possible payload, not a fixed wire
20 size - exactly as for NAV-SAT. storePayload() (in ubxMessageVector.h) already copies only the
21 actual received length, clamped to it.
22*/
