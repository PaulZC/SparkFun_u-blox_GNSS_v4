1/*
2 ubxMONRF.h
3
4 v4 scaffolding: UBX-MON-RF - implemented as its own Class, per AGENTS.md
5 "Implement each UBX message in its own Class". Like MON-COMMS (see ubxMONCOMMS.h), MON-RF's
6 payload is variable length: a fixed 4-byte header (version, nBlocks, reserved0[2]) followed by
7 0..UBX_MON_RF_MAX_BLOCKS identically-shaped 24-byte per-RF-block blocks - see u-blox_structs.h's
8 (removed) UBX_MON_RF_header_t/UBX_MON_RF_block_t and AGENTS.md "Adding the variable-length UBX
9 messages". Nothing new needed designing for the variable-length shape itself - same mechanism as
10 MON-COMMS/NAV-SAT/NAV-SIG/RXM-RAWX/RXM-MEASX/SEC-SIG.
11
12 'ubxFields' below describes the header only, read with the ordinary
13 getUbxMessageField()/getUbxMessageFieldCallback(). 'ubxBlockFields' describes one repeated
14 24-byte RF block, with offsets relative to the START OF THE BLOCK (not the message) - read with
15 getUbxMessageBlockField()/getUbxMessageBlockFieldCallback(), passing the block index
16 (0..nBlocks-1) returned by the "nBlocks" header field above.
17
18 numCallbackCopies is 1 - MON-RF is an ordinary periodic status/diagnostic message (polled or
19 output at a configured rate), not a message that arrives in back-to-back bursts, so the
20 single-slot "latest wins" behavior used by most registered messages is the correct choice here
21 too.
22
23 messageLength is set to UBX_MON_RF_MAX_LEN - the MAXIMUM possible payload (all
24 UBX_MON_RF_MAX_BLOCKS blocks present, currently 2: L1 and L2/L5), not a fixed wire size - exactly
25 as for the other variable-length messages. storePayload() (in ubxMessageVector.h) already copies
26 only the actual received length, clamped to it.
27
28 Replaces the old v3-style getRFinformation(UBX_MON_RF_data_t *data, ...) - which polled with
29 packetCfg/sendCommand() and hand-extracted every field - with the usual getMONRF() thin wrapper
30 around getUBX(). See u-blox_GNSS.h/.cpp.
31*/
