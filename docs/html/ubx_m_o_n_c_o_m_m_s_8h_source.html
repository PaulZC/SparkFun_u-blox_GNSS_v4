1/*
2 ubxMONCOMMS.h
3
4 v4 scaffolding: UBX-MON-COMMS - implemented as its own Class, per AGENTS.md
5 "Implement each UBX message in its own Class". Like NAV-SAT/NAV-SIG/RXM-RAWX/RXM-MEASX/RXM-SFRBX
6 (see ubxNAVSAT.h etc.), MON-COMMS's payload is variable length: a fixed 8-byte header (version,
7 nPorts, txErrors, reserved0, protIds[4]) followed by 0..UBX_MON_COMMS_MAX_PORTS identically-shaped
8 40-byte per-port blocks - see u-blox_structs.h's UBX_MON_COMMS_header_t/UBX_MON_COMMS_port_t and
9 AGENTS.md "Adding the variable-length UBX messages". Nothing new needed designing for the
10 variable-length shape itself - same mechanism as the messages above.
11
12 'ubxFields' below describes the header only, read with the ordinary
13 getUbxMessageField()/getUbxMessageFieldCallback(). 'ubxBlockFields' describes one repeated
14 40-byte port block, with offsets relative to the START OF THE BLOCK (not the message) - read with
15 getUbxMessageBlockField()/getUbxMessageBlockFieldCallback(), passing the block index
16 (0..nPorts-1) returned by the "nPorts" header field above.
17
18 numCallbackCopies is 1 - unlike RXM-SFRBX, MON-COMMS is an ordinary periodic status/diagnostic
19 message (polled or output at a configured rate), not a message that arrives in back-to-back
20 bursts, so the single-slot "latest wins" behavior used by every other registered message is
21 the correct choice here too.
22
23 messageLength is set to UBX_MON_COMMS_MAX_LEN - the MAXIMUM possible payload (all
24 UBX_MON_COMMS_MAX_PORTS ports present), not a fixed wire size - exactly as for the other
25 variable-length messages. storePayload() (in ubxMessageVector.h) already copies only the actual
26 received length, clamped to it.
27*/
