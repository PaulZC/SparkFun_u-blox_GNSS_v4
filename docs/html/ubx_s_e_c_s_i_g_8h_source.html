1/*
2 ubxSECSIG.h
3
4 v4 scaffolding: UBX-SEC-SIG - implemented as its own Class, per AGENTS.md
5 "Implement each UBX message in its own Class". Like NAV-SAT/NAV-SIG/RXM-RAWX/RXM-MEASX/
6 RXM-SFRBX/MON-COMMS (see ubxNAVSAT.h etc.), SEC-SIG's payload is variable length - but only for
7 message Version 3: a fixed 4-byte header (version, sigSecFlags, reserved0, jamNumCentFreqs)
8 followed by 0..UBX_SEC_SEG_MAX_CENT_FREQ_VERSION3 identically-shaped 4-byte per-frequency blocks
9 - see u-blox_structs.h's UBX_SEC_SIG_data_t.versions.version2 (Version 3 reuses this same
10 layout unchanged) and AGENTS.md "Adding the variable-length UBX messages".
11
12 Originally written against Version 2 (0x02), per the field layout documented at the time.
13 Hardware-validated against a real ZED-X20P (CallbackExample9_SECSIG) and found that it actually
14 outputs Version 3 (0x03), not Version 2 - observed sending 7 center frequencies with no jamming
15 present. Version 3's byte layout, per the u-blox X20-HPG-2.11 interface description
16 (UBXDOC-304424225-21617), is identical to Version 2's - the same 4-byte header + repeated
17 4-byte center-frequency block shape - so this class's field tables needed no change, only
18 supportedVersions/messageLength/the block-count constant below being repointed at Version 3.
19 UBX_SEC_SEG_MAX_CENT_FREQ_VERSION3 (u-blox_structs.h) is set to 10, a headroom figure above the
20 7 actually observed, not a documented hard maximum - u-blox hasn't published one for Version 3
21 as far as this engagement has found.
22
23 Only UBX-SEC-SIG Version 3 is supported by this class. Version 1 (a different, fixed 12-byte
24 layout - see UBX_SEC_SIG_data_t.versions.version1 in u-blox_structs.h) is NOT modelled here at
25 all: this class's field tables and byte offsets only make sense for a Version 2/3-shaped
26 payload. A receiver that ever emits Version 1 SEC-SIG would be misparsed by this class (byte 3,
27 read here as jamNumCentFreqs, falls inside Version 1's reserved1[3] and could drive a bogus
28 block count) - not guarded against, since no per-message version dispatch mechanism exists in
29 the registry (see AGENTS.md "Message versioning" - `ubxMessageVersion` is defined but not yet
30 wired up anywhere). A real Version 2 message (if one is ever seen - the ZED-X20P has only been
31 observed sending Version 3) would presumably still parse correctly too, given the identical
32 documented layout, but that hasn't been hardware-tested.
33
34 'ubxFields' below describes the header only, read with the ordinary
35 getUbxMessageField()/getUbxMessageFieldCallback(). 'ubxBlockFields' describes one repeated
36 4-byte center-frequency block, with offsets relative to the START OF THE BLOCK (not the
37 message) - read with getUbxMessageBlockField()/getUbxMessageBlockFieldCallback(), passing the
38 block index (0..jamNumCentFreqs-1) returned by the "jamNumCentFreqs" header field above.
39
40 numCallbackCopies is 1 - like MON-COMMS, SEC-SIG is an ordinary periodic status message, not a
41 message that arrives in back-to-back bursts, so the single-slot "latest wins" behavior used by
42 every other registered message (other than RXM-SFRBX) is the correct choice here too.
43
44 messageLength is set to UBX_SEC_SIG_MAX_LEN_VERSION3 - the MAXIMUM possible payload given the
45 UBX_SEC_SEG_MAX_CENT_FREQ_VERSION3 headroom figure above, not a fixed wire size - exactly as for
46 the other variable-length messages. storePayload() (in ubxMessageVector.h) already copies only
47 the actual received length, clamped to it.
48
49 centFreq is a 24-bit sub-field, wider than any bitfield previously registered in this codebase
50 (every other bitfield sub-field fits within a single byte, so a U1/L-tagged union member alone
51 is enough to read it back correctly). Reading it back needs the FULL 32-bit union member -
52 see ubxAnyType::operator double() in ubxMessage.h - so centFreq is tagged X4/U4, not U1, even
53 though its own bits are confined to 3 of the block's 4 bytes; extractFieldFrom() already always
54 writes the extracted bits into value->U4 regardless of the declared tag, so this only affects
55 which union member the generic double() conversion operator reads back from. Hardware-validated:
56 CallbackExample9_SECSIG printed correct kHz values (e.g. 1575420, 1176450, 1227600, ...) for all
57 7 observed center frequencies, confirming the 24-bit readback works correctly on real hardware.
58*/
