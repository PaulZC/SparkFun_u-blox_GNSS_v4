1/*
2 ubxSECUNIQID.h
3
4 v4 scaffolding: UBX-SEC-UNIQID - implemented as its own Class, per AGENTS.md
5 "Implement each UBX message in its own Class". The payload is a fixed 4-byte header (version,
6 reserved0[3]) followed by the chip's unique ID: 5 bytes on the F9/M9 (version 1, total payload
7 length UBX_SEC_UNIQID_LEN_VERSION1 = 9) or 6 bytes on the M10 (version 2, total payload length
8 UBX_SEC_UNIQID_LEN_VERSION2 = 10) - see u-blox_structs.h's (removed) UBX_SEC_UNIQID_data_t.
9
10 Rather than a fixed 6-byte array field (which would read one stale/uninitialized byte on a
11 version-1 module that only ever sends 5), uniqueId is modelled the same way RXM-PMP's userData/
12 RXM-QZSSL6's msgBytes are: as 0..6 repeated 1-byte "blocks", one field ("byte") each. This is
13 also exactly ESF-RAW's case (see AGENTS.md "Adding support for ESF-RAW and ESF-STATUS"): there
14 is no header field carrying the byte count, so getUbxMessageBlockCount()/...Callback() fall back
15 to deriving it purely from the actual received length (5 for version 1, 6 for version 2) -
16 blockCountField is left at its default nullptr, same as ESF-RAW.
17
18 numCallbackCopies is 1 - like MON-HW/MON-HW2/MON-RF, this is a poll-only status message, not a
19 message that arrives in bursts.
20
21 There are no CFG-MSGOUT-UBX-SEC-UNIQID-* keys - the chip ID never changes, so u-blox gives this
22 message no periodic-output configuration at all; it can only be polled. msgOutKeys stays
23 all-zero, same convention as HNR-ATT/HNR-INS/HNR-PVT (see AGENTS.md).
24
25 Replaces the old v3-style getUniqueChipId(UBX_SEC_UNIQID_data_t *data, ...)/
26 getUniqueChipIdStr(UBX_SEC_UNIQID_data_t *data, ...) (which polled with packetCfg/sendCommand()
27 and hand-extracted every byte, returning a static char buffer) with the usual getSECUNIQID()
28 thin wrapper around getUBX(), plus a getUniqueChipIdStr() helper that reads the 6 "byte" blocks
29 and returns them as a 12-character hex String (e.g. "0123456789AB"). See u-blox_GNSS.h/.cpp.
30*/
