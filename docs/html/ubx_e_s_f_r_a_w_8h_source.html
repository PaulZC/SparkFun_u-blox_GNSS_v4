1/*
2 ubxESFRAW.h
3
4 v4 scaffolding: UBX-ESF-RAW - implemented as its own Class, per AGENTS.md "Implement each UBX
5 message in its own Class". Like NAV-SAT/NAV-SIG/RXM-RAWX/RXM-MEASX/RXM-SFRBX/MON-COMMS/SEC-SIG/
6 ESF-MEAS (see ubxNAVSAT.h etc.), ESF-RAW's payload is variable length: a 4-byte header (all
7 reserved - see below) followed by 0..DEF_NUM_SENS*DEF_MAX_NUM_ESF_RAW_REPEATS identically-shaped
8 8-byte raw-sensor-measurement blocks - see u-blox_structs.h's UBX_ESF_RAW_data_t/
9 UBX_ESF_RAW_sensorData_t and AGENTS.md "Adding the variable-length UBX messages".
10
11 ESF-RAW is unlike every other variable-length message registered so far: its 4-byte header is
12 ENTIRELY reserved - there is no block-count field anywhere in the wire format at all. The old
13 v3 struct even says so explicitly: "UBX_ESF_RAW_data_t.numEsfRawBlocks: Note: this is not
14 contained in the ESF RAW message. It is calculated from the message length." So there is no
15 header field for a caller to read and loop on (unlike MON-COMMS's "nPorts" or SEC-SIG's
16 "jamNumCentFreqs") - getUbxMessageBlockCount()/...Callback() (ubxMessage::getBlockCount()) is
17 the ONLY way to know how many blocks are actually present in a particular message, and it now
18 falls back to computing this purely from the real received byte length when no block-count
19 field is set (see the extended comment on getBlockCount() in ubxMessage.h) - this class leaves
20 'blockCountField' at its default (nullptr) specifically to use that fallback. numFields is 0 and
21 'ubxFields' is passed as nullptr, since there is nothing in the 4-byte header worth exposing as
22 a named field.
23
24 Per AGENTS.md/the user's explicit instruction: the u-blox_structs.h comment above
25 UBX_ESF_RAW_MAX_LEN notes "the NEO-M8U sends them in sets of ten (i.e. seventy readings per
26 message)" - this is about how many BLOCKS one single ESF-RAW message can contain (which
27 messageLength/maxBlocks below already size for, unchanged), not about needing multiple
28 _callbackStorage ring-buffer copies the way RXM-SFRBX/ESF-MEAS do for a burst of separate
29 MESSAGES arriving together. numCallbackCopies is 1 - explicitly instructed - the single-slot
30 "latest wins" behavior used by most registered messages is correct here.
31
32 'ubxBlockFields' describes one repeated 8-byte raw-sensor-measurement block, with offsets
33 relative to the START OF THE BLOCK (not the message) - read with
34 getUbxMessageBlockField()/getUbxMessageBlockFieldCallback(), passing a block index up to (but
35 not including) getUbxMessageBlockCount()/...Callback()'s count.
36
37 dataField is a 24-bit sub-field, the same width/tagging concern as ESF-MEAS's dataField and
38 SEC-SIG's centFreq - it needs the FULL 32-bit union member to read back correctly (X4/U4, not
39 U1) - see ubxSECSIG.h's file header comment for the full explanation of why. dataType here is a
40 full 8-bit sub-field (unlike ESF-MEAS's 6-bit dataType), so U1 is correct for it directly.
41
42 messageLength is set to UBX_ESF_RAW_MAX_LEN - the MAXIMUM possible payload (4-byte header + all
43 DEF_NUM_SENS*DEF_MAX_NUM_ESF_RAW_REPEATS blocks), not a fixed wire size - exactly as for the
44 other variable-length messages. storePayload() (in ubxMessageVector.h) already copies only the
45 actual received length, clamped to it, and records that actual length in _actualLength/
46 _callbackActualLength for getBlockCount()'s length-only fallback to use.
47
48 ESF-RAW data cannot be polled - it is "Output" only (see the comment above the real ESF-RAW
49 section in u-blox_structs.h) - so, unlike ESF-STATUS/MON-COMMS/SEC-SIG, there is no getESFRAW()
50 poll wrapper: the old v3 API never had one either, only the automatic/callback path applies.
51*/
